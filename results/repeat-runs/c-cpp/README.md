# Repeat runs of the C/C++ triggers under TSan

Each trigger was run 20 times on all CPUs and 20 times pinned to one CPU with
`taskset -c 0`, with `TSAN_OPTIONS="halt_on_error=1 exitcode=66"` and a 60 s
timeout. `summary.tsv` records each run's exit code, duration and whether its
log has a TSan data race report.

| Case | CPUs | Runs with a TSan report |
|---|---|---|
| `xz-mt-decoder-2026` (`xz -dc -T4 multi-4KiB.xz`) | all | 20 of 20 |
| `xz-mt-decoder-2026` (`xz -dc -T4 multi-4KiB.xz`) | one | 1 of 20 |
| `rocksdb-inplace-update-2024` (`rocksdb-inplace-update 1 1`) | all | 20 of 20 |
| `rocksdb-inplace-update-2024` (`rocksdb-inplace-update 1 1`) | one | 20 of 20 |

The input is the same in each pair of rows, so the liblzma race depends on the
schedule inside its gate (shape C), while the RocksDB race does not (shape B).

Binaries: `xz` 5.8.3 built with `-fsanitize=thread`, and the RocksDB harness
built with TSan, as described in the harness READMEs. The input
`multi-4KiB.xz` (6,596,724 bytes) is generated by
`harnesses/c/xz-mt-decoder-2026/make-inputs.sh`.

```bash
env TSAN_OPTIONS="halt_on_error=1 exitcode=66" timeout -k 5s 60s \
  [taskset -c 0] build-tsan/xz -dc -T4 multi-4KiB.xz > /dev/null
env TSAN_OPTIONS="halt_on_error=1 exitcode=66" timeout -k 5s 60s \
  [taskset -c 0] rocksdb-inplace-update-tsan 1 1
```
