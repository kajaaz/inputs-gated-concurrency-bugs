# Zorya on the C (liblzma) and C++ (RocksDB) harnesses

`run.sh` runs `zorya <bin> --analysis data-race --arg ...` on the trigger and on
one benign input of each harness. No run reached a thread creation, so these
harnesses appear as "n/a" for Zorya in the paper's table.

| Build | Harness | Outcome |
|---|---|---|
| PIE, dynamic (`pie-attempt/`) | both | Zorya loaded `main` at its unrelocated address; the run stopped on an out-of-bounds read. Reported status `no_concurrency` is an artefact. |
| non-PIE, `-Wl,-z,now` (`summary.tsv`, `logs/`) | liblzma | `fopen` is an unmodelled libc call: Zorya skips it and returns 0, and the harness dereferences the NULL `FILE *` (exit 1, about 38 s). |
| non-PIE, `-Wl,-z,now` | RocksDB | `mkdtemp` is skipped and returns 0, so the harness exits before it starts the reader threads; status `no_concurrency` (75 s). The benign run was stopped. |
| static (`static-probe/`) | liblzma, trigger | glibc's `fopen` reaches the `openat` syscall, where Zorya hangs: its handler locks the CPU state that the caller already holds. Killed after about 4 minutes. glibc's `pthread_create` would next issue `clone3`, which Zorya does not handle. |

With dynamic linking, Zorya's C model executes only `pthread_create` and
`pthread_join` of libc; every other libc call returns 0. Its C race tests
(`tests/programs/race-counter-c*`) avoid other libc calls on the racing path.

Binaries and Zorya's per-run output directories are not included; the input
files are generated by `harnesses/c/xz-mt-decoder-2026/make-inputs.sh`.
